MeisterCharts · Konzept

Test-Infrastruktur für Interaktionen

Wie 100 % der Gesten in der PV-Modulplanung und der String-Planung abgedeckt werden — stabil, schnell und ohne dass jemand Pixelkoordinaten pflegen muss.

1Warum die vorhandenen Tests nicht reichen

Nach dem Umbau auf InteractionTool gibt es 118 Tests. Sie prüfen die Werkzeuge isoliert: Ein InteractionTarget geht rein, eine Liste von Commands kommt raus. Das ist wertvoll und schnell, deckt aber genau die Kette nicht ab, in der der zuletzt gefundene Defekt saß.

KettengliedHeute abgedecktWas ungetestet bleibt
InteractionTool ja —
Command + CommandExecutor ja —
InteractionTargets ja synthetische Rechtecke, nicht die echte Layout-Geometrie
Registrierung in layout() nein Ein Button wird gemalt, aber nicht registriert — oder umgekehrt
CanvasDragSupport + Broker-Reihenfolge nein Down auf Button startet fälschlich einen Drag; Handler-Reihenfolge kippt
Zusammenspiel zweier Layer nein beginLayout() im falschen Layer räumt die Regionen des anderen weg
Resize über ResizeHandlesSupport nein Achsenorientierung, Handle-Richtung, Clamping am Dachrand

Der Kern des Problems

Ein Tool-Test kann nicht fehlschlagen, wenn ein Delete-Button an der falschen Stelle registriert wird — er bekommt das InteractionTarget ja geschenkt. Genau diese Klasse von Fehlern ist die, die Nutzer sehen.

2Was „eine Geste“ ist

Ohne Definition ist „100 %“ nicht messbar. Für dieses Konzept gilt:

Eine Geste ist eine Sequenz von Eingabe-Events, die auf einem definierten Vorzustand zu einem fachlichen Ergebnis führt — beschrieben durch das getroffene Element, die getroffene Handle-Rolle und den Vorzustand des Charts.

Daraus folgt die Abdeckungsmatrix. Sie ist ein Kreuzprodukt, keine Wunschliste: 

// Modulplanung
Element   ∈ { ModuleArea, UnusableArea, Module, — }
Rolle     ∈ { Body, DeleteButton, RotateButton, ResizeHandle, — }
Vorzustand∈ { leer, selektiert, fremd-selektiert, dragging, Modul gelöscht }
Modus     ∈ { Planning, Rendering, Printing }

// String-Planung
Element   ∈ { Modul in aktivem String, Modul in fremdem String, freies Modul, — }
Vorzustand∈ { kein String aktiv, String aktiv }

Das Kreuzprodukt hat mehr Zellen, als sinnvolle Gesten existieren. Jede Zelle bekommt deshalb genau eines von zwei Urteilen: abgedeckt mit Testfall, oder nicht anwendbar mit Begründung — etwa „Sperrflächen haben keinen Rotate-Button“. Kein stilles Weglassen. Das ist die eigentliche 100-%-Garantie: nicht Fleiß, sondern eine vollständig aufgezählte Matrix mit einem Urteil pro Zelle.

3Die vier Bausteine

1

GestureCatalog — die Matrix als Daten

Jede Geste ist ein Eintrag mit Id, Beschreibung und Skript. Der Katalog ist die einzige Quelle dafür, was „alle Gesten“ heißt. Neue Geste = neuer Eintrag; die Vollständigkeitsprüfung zieht daraus.

2

PlanningChartRobot — echte Events, semantische Ziele

Speist Maus- und Tastatur-Events in einen headless aufgebauten Chart, durch die vollständige echte Kette. Ziele werden semantisch benannt (on(moduleArea, DeleteButton)) und vom Robot über die Registry in Koordinaten aufgelöst.

3

ChartStateSnapshot — ein lesbarer Textabzug

Nach jeder Geste: Modell, Interaktionszustand, Undo-Stack und Cursor als normalisierter Text. Ein Blick ins Diff genügt, um zu sehen, was eine Änderung angerichtet hat.

4

GestureInvariants — Regeln, die für jede Geste gelten

Undo-Rundlauf, Hover-Idempotenz, kein Zustandsleck nach Abbruch, Untätigkeit außerhalb des Planungsmodus. Laufen automatisch über den ganzen Katalog — eine neue Geste erbt sie, ohne dass jemand einen Test schreibt.

4Der Robot: semantische Ziele statt Pixel

Die Infrastruktur steht bereits fast vollständig bereit. MockCanvas, ChartSupport und das paintingContext-Muster aus ValueAxisWithOffsetLayerPaintTest.kt:106 laufen headless und liegen sämtlich in commonMain, sind also auf JVM und JS verfügbar; DefaultMouseEventBroker.notifyDown / notifyMove / notifyUp ist der Einspeisepunkt, LayerList verteilt an die Layer. Was fehlt, ist die Klammer darum. 

class PlanningChartRobot<E : Any, M : Any>(
  gestalt: ChartGestalt,
  canvasSize: Size = Size(800.0, 600.0),
) {
  /** Layout + Events, wie im echten Chart. Löst semantische Ziele über die Registry auf. */
  fun hover(target: GestureTarget<E>)
  fun press(target: GestureTarget<E>)
  fun dragBy(distance: @RoofRelative @mm Distance)   // Dach-Millimeter, keine Pixel
  fun release()
  fun key(keyStroke: KeyStroke)
  fun undo()
  fun redo()

  fun snapshot(): ChartStateSnapshot
}

sealed interface GestureTarget<out E : Any> {
  data class On<E : Any>(val element: E, val role: HandleRole) : GestureTarget<E>
  data object Nothing : GestureTarget<kotlin.Nothing>      // leere Dachfläche
  data object OutsideCanvas : GestureTarget<kotlin.Nothing>  // Maus verlässt den Canvas
}

Der Robot führt vor jedem Event einen echten Layout-Durchlauf aus — genau wie der Canvas es tut. Dadurch stimmt die Registry immer mit dem Modellzustand überein, und ein Test, der ein Modul verschiebt und danach dessen Delete-Button drückt, trifft ihn an der neuen Stelle.

Der wichtigste Effekt

Löst On(moduleArea, DeleteButton) keine registrierte Region auf, schlägt der Test mit „Für ModuleArea ist kein DeleteButton registriert“ fehl — nicht mit einem stillen Klick ins Leere. Damit ist „gemalt, aber nicht klickbar“ eine Testfehlermeldung statt eines Bug-Reports.

Nichts davon ist neu erfunden

Die semantischen Ziele sind keine Test-Erfindung: InteractionTarget(element, role, bounds) und HandleRole existieren bereits im Produktionscode und sind das Vokabular, in dem die Werkzeuge ohnehin denken. Die Registry löst heute Koordinate → Ziel auf; der Robot braucht zusätzlich die Umkehrung Ziel → Koordinate. Das ist eine Sichtbarkeitsfrage (interactionTargets für den Robot erreichbar machen) plus die Punktsuche unten — kein zweites Modell neben dem Produktionsmodell.

Was ein Spike sofort aufgedeckt hat

Der naive Ansatz „nimm die Mitte des Elements“ ist falsch: In der Mitte einer Modulfläche sitzt ihr Delete-Button. Ein Klick dorthin löscht sie, statt sie zu greifen — beim Schreiben des Spikes ist genau das passiert, obwohl der Autor den Code am Vortag selbst gebaut hatte.

Der Robot probiert deshalb mehrere Punkte im Element (Mitte, dann Richtung Ecken) und nimmt den ersten, an dem findTargetAt wirklich das gewünschte Element mit der gewünschten Rolle liefert. Findet er keinen, ist das ein Testfehler: „Kein Punkt gefunden, an dem ModuleArea als Body getroffen wird“ — ein vollständig von Buttons verdecktes Element ist ein echter Bedienfehler.

Muss MockCanvas dafür ausgebaut werden? Nein.

Die naheliegende Sorge ist, dass ein headless Chart eine tragfähige Canvas-Attrappe braucht — mit Font-Metriken, Bildern, Rendering. Ein lauffähiger Spike gegen den echten PvModulePlanningLayer zeigt: nichts davon.

BefürchtungRealität im Spike
Rendering muss funktionieren paint() wird nie aufgerufen. Regionen entstehen in layout() — nur das läuft.
Font-Metriken werden gebraucht Die Regionen kommen aus Icon-Größen (Size.PX_24, Size.PX_30), nie aus Textbreiten.
MockCanvas muss erweitert werden Unverändert benutzbar, zusammen mit MockCanvasRenderingContext und ChartSupport.
MeisterChartsPlatform.init() nötig Nein — das gibt es nur für JavaFX und JS. Es braucht eine Zeile (siehe unten).

Die einzige Plattform-Abhängigkeit: PvRoofPlanningLayer.Configuration legt beim Konstruieren die Panel-PNGs als LocalResourcePaintable an, und deren Konstruktor fragt eine Factory. Sie ist eine var und im Test in einer Zeile gesetzt: 

MeisterchartsJvm.localResourcePaintableFactory =
  JvmLocalResourcePaintableFactory { _, _, _ -> Paintable.NoOp }

Der gesamte Spike — Chart aufbauen, layouten, Punkt suchen, Down schicken, Zustand prüfen — ist 98 Zeilen. Er hat auf Anhieb die Kette Layout → Registry → Broker → DragSupport → Tool → Command durchlaufen und dabei den Mitte/Delete-Button-Fallstrick aufgedeckt. Der Robot ist im Wesentlichen dieser Spike, aufgeräumt und wiederverwendbar.

5So sieht ein Test aus

@Test
fun `Sperrfläche über den Dachrand hinaus ziehen wird begrenzt`() {
  val robot = modulePlanningRobot(PvRoofSampleModels.realistic())

  robot.press(on(unusableArea, HandleRole.Body))
  robot.dragBy(Distance(99_000.0, 0.0))
  robot.release()

  // Eine explizite Kern-Aussage: worum es in dieser Geste geht
  assertThat(unusableArea.location.x)
    .isLessThanOrEqualTo(model.roofSize.width - unusableArea.size.width)

  // Plus der Zustandsabzug für alles Drumherum
  robot.snapshot().matchesGolden("unusable-area-drag-clamped")

Warum nicht nur Golden Master

Reine Snapshot-Tests verrotten: Bei einem roten Test wird der Abzug erneuert, ohne ihn zu lesen. Deshalb hat jede Geste zusätzlich mindestens eine explizite Zusicherung zu ihrem Kern. Der Snapshot ist das Sicherheitsnetz für unbeabsichtigte Nebenwirkungen, nicht der Test selbst.

6Wie 100 % gemessen werden

Drei Ebenen, die sich gegenseitig absichern:

EbenePrüfungFängt
Katalog Meta-Test: Jeder GestureId ist mindestens ein ausgeführter Test zugeordnet. Geste beschrieben, aber nie getestet
Matrix Meta-Test: Jede Zelle des Kreuzprodukts trägt ein Urteil — abgedeckt oder begründet nicht anwendbar. Geste gar nicht erst gedacht
Kover 100 % Branch-Coverage auf canvas/interaction/, canvas/command/, *Tool.kt, *Commands.kt, *VisualStates.kt. Zweig, den die Matrix nicht kennt

Die mittlere Ebene ist der Kern. Der Matrix-Test bekommt die Achsen als Aufzählungen und bildet das Kreuzprodukt selbst — wächst HandleRole um einen Wert, werden schlagartig alle neuen Kombinationen rot, bis jemand pro Zelle entschieden hat. Das ist der Unterschied zwischen „wir haben 50 Tests“ und „es gibt nachweislich keine 51.“ 

@Test
fun `jede Kombination aus Element, Rolle und Vorzustand hat ein Urteil`() {
  val offen = GestureMatrix.allCells() - GestureCatalog.judgedCells()

  assertThat(offen).isEmpty()   // Meldung listet die offenen Zellen einzeln auf
}

7Stabilität: was ein Test niemals enthält

VerbotenStattdessen
Pixelkoordinaten on(element, role) — der Robot fragt die Registry
Drag-Distanzen in Pixeln dragBy in Dach-Millimetern; der Robot rechnet um
Zufalls-UUIDs feste UUIDs aus dem Testmodell; Snapshots zeigen #1, #2
Wanduhr-Zeit nowProvider festnageln; Event-Zeitstempel zählt der Robot hoch
toString() auf Double oder Domänenobjekten im Snapshot eigene Formatierung auf ganze Millimeter — siehe Abschnitt 8, das ist zwingend
Canvas-Größe implizit fest im Robot; Charts sind zoom-frei und passen sich der Dachgröße an

Diese Regeln sind der Grund, warum die Suite eine Layout-Änderung übersteht: Verschiebt sich der Rotate-Button an eine andere Ecke, ändert sich kein einziger Test — nur die Registrierung im Layer, und die Registry liefert die neue Position an alle Tests aus.

8Auf welcher Plattform laufen die Tests

Die naheliegende Antwort wäre JVM — schnell, IDE-Integration, Debugger. Sie ist falsch, und der Grund steht im Source-Set-Zuschnitt der konsumierenden Anwendung: commonMain, jsMain, jsTest — kein jvmMain. Die Planungs-Charts werden ausschließlich als Kotlin/JS ausgeliefert. Getestet wird heute ausschließlich auf der JVM. Wir prüfen also eine Plattform, die nie beim Kunden läuft.

Gemessene Unterschiede

Eine Probe mit identischem Quelltext in jvmTest und jsTest von meistercharts-canvas ergab:

AusdruckJVMJS (Node)Gleich
1.0.toString()1.01nein
Coordinates(400,7200)400.0/7200.0400/7200nein
Size(1000,1400)1000.0x1400.01000x1400nein
(-0.0).toString()-0.00nein
10000.0 / 3.03333.3333333333335ja
0.1 + 0.20.30000000000000004ja
(11200.0/1020.0).toIntFloor()10ja

Das Muster ist eindeutig: Die Arithmetik ist bitgenau identisch — beide Plattformen rechnen IEEE-754-Doubles. Abweichend ist ausschließlich die Textdarstellung von Zahlen. Damit sind Hit-Test, Layout-Rechnung, Tool-Logik und Commands plattformunabhängig; die Gestenlogik verhält sich auf JS garantiert wie auf der JVM.

Zwingende Folge für den Snapshot

Ein Golden Master, der toString() auf Double, Coordinates oder Size aufruft, ist auf JVM und JS unterschiedlich — man bräuchte zwei Sätze Golden Files, und der Wert der Methode wäre dahin. Der Snapshot muss deshalb selbst formatieren: auf ganze Millimeter runden und als Int ausgeben. Das war im Entwurf eine Stilfrage — nach dieser Messung ist es eine Bedingung.

Die Empfehlung: commonTest, eine Quelle, zwei Läufe

Die Gesten-Suite gehört nach commonTest und läuft auf beiden Plattformen — nicht als Kompromiss, sondern weil beide unterschiedliche Fragen beantworten:

LaufDauerRolle
JVM ~7–14 s Der Entwicklungs-Loop. Einzelne Tests über --tests filterbar, Debugger und IDE-Integration vorhanden. Hier arbeitet man.
JS (Node) ~53 s Das Merge-Gate. Die Plattform, die tatsächlich ausgeliefert wird. Läuft in der Pipeline, nicht bei jedem Speichern.

Technisch ist das tragfähig: MockCanvas, MockCanvasRenderingContext und ChartSupport liegen in commonMain, der Robot ist also multiplattform-fähig. kotlin.test ist auf der JVM lauffähig (per Probe bestätigt), und AssertK ist als Multiplattform-Artefakt eingebunden — kotlin-events, kotlin-lang und math nutzen es bereits in commonTest.

Was das kostet

  • meistercharts-pv-planning hat bislang weder commonTest noch jsTest — beide Verzeichnisse müssen angelegt werden.
  • Die 118 bestehenden Tests nutzen org.junit.jupiter.api.Test. Sollen sie mitwandern, ist das ein mechanischer Import-Tausch auf kotlin.test.Test. Kein Muss — sie können bleiben, wo sie sind; nur die neue Gesten-Suite muss gemeinsam sein.
  • jsTest kennt keine --tests-Filterung, nur der Task jsNodeTest. Ein weiterer Grund, den JS-Lauf nicht zum Arbeits-Loop zu machen.

Browser-Tests: bewusst klein gehalten

Auch der JS-Lauf läuft unter Node, nicht im Browser (jsBrowserTest ist SKIPPED). Ungetestet bleibt damit die Brücke von echten Pointer-Events zu MouseDownEvent & Co.

Dafür genügt eine Handvoll Playwright-Tests — ein Drag, ein Button-Klick, ein Tastendruck je Chart. Die Gesten-Matrix über den Browser zu fahren wäre um Größenordnungen langsamer, flaky und würde nichts zusätzlich absichern, weil die Logik nachweislich plattformgleich rechnet. Vollständigkeit in commonTest, Realitätsnachweis im Browser.

SchrittInhaltErgebnis

Die Schritte 1 und 2 sind die Investition — danach kostet eine zusätzliche Geste drei bis fünf Zeilen und erbt Undo-Prüfung, Snapshot und Matrix-Buchführung automatisch. Genau das macht die 100 % erreichbar und haltbar: Nicht die erste vollständige Suite ist das Problem, sondern die zweihundertste Änderung danach.
